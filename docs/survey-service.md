# Опросы пользователей на сайте (survey-service)

Рабочий документ для обсуждения и последующей разработки. Фиксирует принятые решения, логику работы, модель данных, тонкие места и вопросы, которые нужно закрыть до старта. Код и конкретная реализация определяются после ревью бэкенда, техлида и фронта.

---

## 1. Цель

Показывать на сайте поп-ап с опросом (CES и NPS) на заданных шагах флоу клиента, сохранять оценки в собственной БД и передавать их в DWH с привязкой к клиенту, его займам и этапам воронки.

Сервис только собирает оценки. Расчет NPS, CES и любых других метрик делается в BI на сырых данных из DWH.

## 2. Объем первой версии

Входит:
- поп-ап опроса на сайте (десктоп и мобильная версия сайта);
- несколько опросов, каждый привязан к одному или нескольким шагам флоу;
- опросы из одного или нескольких шагов (на макете два шага, индикатор «1/2»): шаг 1 — NPS, шаг 2 — CES;
- несколько типов вопросов по макетам из Figma;
- правила показа: на каком событии, кому, не чаще чем раз в день;
- гибкие условия показа (тип клиента, продукт, канал, доля показа);
- хранение показов, закрытий и ответов;
- загрузка сырых данных в DWH.

Не входит в первую версию:
- мобильное приложение (почти все клиенты пользуются сайтом);
- промокоды и любые награды за ответ;
- админка для управления опросами (на старте опросы заводятся разработчиком через миграции);
- A/B тесты разных формулировок;
- расчет метрик на стороне сервиса (делает BI).

Архитектура должна позволять добавить эти пункты позже без переделки основной логики.

## 3. Принятые решения

| Вопрос | Решение | Обоснование |
|---|---|---|
| Готовый сервис опросов или своя разработка | Своя разработка | Данные остаются в собственной БД и в контуре компании, прямая связь с клиентом и DWH |
| Нужен ли бэкенд | Да | Прямая запись в БД с фронта требует открытых доступов к БД. Правила показа и привязка к клиенту требуют серверной логики. Без бэкенда ответы можно подделать от имени другого клиента |
| Микросервис или модуль | Изолированный сервис опросов со своей схемой БД и своим набором эндпоинтов, без зависимостей от кода других сервисов | Бэкенд уже на микросервисах, новый сервис по стандартному шаблону не требует новой инфраструктуры. Альтернатива для обсуждения с техлидом: изолированный модуль в бэкенде сайта (BFF), если такой слой есть |
| Платформы | Только сайт | Почти все клиенты на сайте, приложение можно добавить позже |
| Промокоды | Нет | Упрощает первую версию |
| Метрики опроса | CES и NPS | CES — легкость прохождения шага, NPS — лояльность |
| Шкала оценки | Задается в настройках каждого вопроса. NPS: 1–10, радиокнопки. CES: 1–5, смайлики (по макету) | Решение продукта: шкала как в макете. Стандартный NPS — 0–10, перейти на него можно настройкой вопроса без релиза |
| Комментарий | Показывается только при низкой оценке: NPS 6 и ниже, CES 3 и ниже (по макету) | Условие задается в настройках вопроса (showIf), пороги меняются без релиза |
| Порядок шагов | Шаг 1 — NPS, шаг 2 — CES (по макету) | Задается в конфигурации опроса |
| Расчет метрик | В BI, сервис хранит только сырые оценки | Логику расчета можно менять без релиза сервиса |
| Частота показа | При каждом новом наступлении события, но не чаще 1 раза в день на один опрос | Оценка привязана к конкретному событию, клиент не перегружается опросами |
| Лимиты показов и паузы после закрытия | Не используются | Заменены правилом «не чаще 1 раза в день» |
| Добавление новых опросов | Через конфигурацию в БД, без релиза фронта | Релиз фронта нужен только при появлении нового типа вопроса |
| Персональные данные | Отдельная обработка не требуется | Клиент дает согласие на обработку ПД при входе на сайт, данные не покидают контур компании |
| Отказоустойчивость | Сбой сервиса опросов никак не влияет на флоу клиента | Опрос вторичен по отношению к выдаче займа |

## 4. Общая схема работы

Участники: сайт (фронт), сервис опросов (бэкенд), БД сервиса, DWH, BI.

Последовательность:

1. Клиент доходит до шага флоу, на котором может быть опрос (на старте — погашение займа).
2. Фронт запрашивает у сервиса опросов активный опрос для этого шага, передавая код шага и, если есть, ID объекта события (например, ID займа).
3. Сервис определяет клиента по сессии, проверяет правила показа и возвращает либо полную конфигурацию опроса (шаги, вопросы, типы, тексты, настройки), либо ответ «опроса нет».
4. Если опроса нет, фронт ничего не делает.
5. Если опрос есть, фронт показывает поп-ап и сообщает сервису о факте показа. Сервис создает запись показа и возвращает ее идентификатор.
6. Клиент отвечает на первый шаг (например, CES) и нажимает «Отправить». Фронт отправляет ответы этого шага, привязывая их к идентификатору показа. Сервис проверяет и сохраняет ответы.
7. Аналогично для следующих шагов (например, NPS).
8. После последнего шага сервис сам переводит показ в статус «завершен», фронт показывает экран благодарности.
9. Если клиент закрыл поп-ап крестиком, фронт сообщает сервису о закрытии и номере шага, на котором это произошло. Ответы на уже пройденные шаги сохраняются.
10. Данные из БД сервиса регулярно загружаются в DWH, метрики считает BI.

## 5. Сущности и модель данных

Описание логической модели. Типы полей, индексы и конкретная СУБД определяются бэкендом.

### 5.1. Опрос

| Поле | Назначение |
|---|---|
| Идентификатор | Внутренний ID |
| Код | Уникальный человекочитаемый код, например nps_ces_loan_repaid. Используется в аналитике и логах, не должен меняться |
| Название | Заголовок поп-апа («Пройдите опрос») |
| Статус | Черновик / активен / архив |
| Приоритет | Используется, если на одном шаге подходит несколько опросов |
| Минимальный интервал между показами | По умолчанию 1 календарный день. Опрос показывается клиенту не чаще этого интервала |
| Дата начала и окончания | Опрос активен только в этом интервале. Можно не заполнять |
| Даты создания и изменения | Служебные |

### 5.2. Вопрос

| Поле | Назначение |
|---|---|
| Идентификатор | Внутренний ID |
| Опрос | К какому опросу относится |
| Код | Человекочитаемый код вопроса, например ces, nps, nps_comment. По нему BI отличает метрики |
| Метрика | CES / NPS / другое. Упрощает фильтрацию в BI |
| Номер шага | На каком шаге опроса показывается (1, 2 и т. д.) |
| Позиция | Порядок вопроса внутри шага |
| Тип | Шкала, текст, выбор одного, выбор нескольких, звезды (итоговый список по Figma) |
| Текст | Формулировка вопроса |
| Обязательность | Нельзя отправить шаг без ответа |
| Настройки | Набор параметров, зависящий от типа: границы шкалы и подписи к краям, вид шкалы (цифры или смайлики), плейсхолдер и максимальная длина текста, список вариантов с кодом и подписью, максимум выбранных вариантов. Условие показа showIf: вопрос виден, только если ответ на другой вопрос подходит, например `{"question": "nps", "op": "lte", "value": 6}` |

### 5.3. Триггер

Связь опроса с шагом флоу и условия показа.

| Поле | Назначение |
|---|---|
| Опрос | Какой опрос показывать |
| Код шага флоу | Например registration_completed, loan_issued, loan_repaid |
| Условия | Гибкое правило (см. п. 6.2) |
| Доля показа | Процент клиентов, которым показывается опрос, из тех, кто подходит под условия. По умолчанию 100% |

Один опрос может иметь несколько триггеров, один шаг флоу может быть триггером нескольких опросов.

### 5.4. Показ

Каждый факт показа опроса клиенту. Центральная сущность для аналитики.

| Поле | Назначение |
|---|---|
| Идентификатор | Уникальный ID, генерируется сервисом. Используется фронтом для отправки ответов |
| Опрос | Какой опрос показан |
| Клиент | ID клиента |
| Код шага флоу | На каком шаге флоу показан |
| ID объекта события | Например ID займа или заявки. Нужен для связи оценки с конкретным займом в DWH. Можно не заполнять |
| Статус | Показан / закрыт / завершен |
| Последний шаг | Номер последнего шага опроса, на который клиент ответил |
| Шаг закрытия | Номер шага, на котором клиент закрыл поп-ап (если закрыл) |
| Даты создания и изменения | Служебные |

### 5.5. Ответ

Ответ на один вопрос в рамках одного показа.

| Поле | Назначение |
|---|---|
| Идентификатор | Внутренний ID |
| Показ | К какому показу относится |
| Опрос | Дублируется из показа для удобства в DWH |
| Вопрос | На какой вопрос ответ |
| Клиент | Дублируется из показа для удобства в DWH |
| Числовое значение | Для шкалы и звезд |
| Текстовое значение | Для комментария |
| Выбранные варианты | Коды вариантов для выбора одного и выбора нескольких (массив) |
| Даты создания и изменения | Служебные |

У каждого ответа заполнено только одно поле значения, в зависимости от типа вопроса. Отдельные колонки вместо одного универсального поля нужны, чтобы в DWH и BI оценки читались как числа без разбора по типу вопроса.

Пара «показ + вопрос» уникальна: на один вопрос в одном показе хранится один ответ.

Опрос и клиент дублируются в ответах намеренно, чтобы в DWH ответы читались без лишних связей между таблицами.

### 5.6. Результат по вопросу

Результат определяется отдельно по каждому вопросу, а не по показу целиком.

| Результат | Условие |
|---|---|
| Ответил | По вопросу есть ответ |
| Закрыл | Ответа нет, клиент закрыл поп-ап на шаге этого вопроса или раньше |
| Не дошел | Ответа нет, показ остался в статусе «показан» (клиент закрыл вкладку, обновил страницу) |

Пример: опрос из двух шагов, шаг 1 — NPS, шаг 2 — CES (как в макете). Клиент ответил на NPS и закрыл поп-ап на шаге CES. Результат: NPS «ответил», CES «закрыл». При обратном порядке шагов — наоборот.

Результат можно не хранить, а вычислять в DWH или BI по ответам и полям показа. Решение за DWH.

## 6. Правила показа

### 6.1. Основные правила

Опрос возвращается клиенту, только если выполнены все условия:

1. Опрос в статусе «активен».
2. Текущая дата попадает в интервал действия опроса (если интервал задан).
3. У опроса есть триггер с переданным кодом шага флоу.
4. Клиент подходит под условия триггера (п. 6.2).
5. Клиент попал в долю показа триггера.
6. Этот опрос не показывали клиенту в текущий календарный день (или в течение минимального интервала опроса, если он больше дня).

Опрос показывается при каждом новом наступлении события. Если клиент сегодня получил займ и ответил на опрос, а завтра получил новый займ, опрос показывается снова. Прошлые ответы и закрытия на показ не влияют.

Лимиты на общее число показов, пауза после закрытия и общая пауза между разными опросами не используются.

Если подходит несколько опросов, возвращается один, с наибольшим приоритетом. При равном приоритете выбор должен быть детерминированным (например, более старый опрос).

Граница календарного дня считается по московскому времени, чтобы «один раз в день» совпадало с ощущением клиента. Время в БД хранится в UTC.

### 6.2. Гибкие условия показа

Условия триггера задаются набором правил в конфигурации, без релиза. Правила объединяются через «И».

Атрибуты для условий на старте:

| Атрибут | Пример значения |
|---|---|
| Тип клиента | Новый / повторный |
| Продукт | PDL / IL |
| Канал привлечения | Органика, партнеры, реклама |
| Номер займа клиента | 1, 2–5, больше 5 |
| Доля показа | 30% |

Операторы: равно, не равно, входит в список, больше, меньше.

Пример: показывать CES+NPS после выдачи займа повторным клиентам с продуктом PDL, 50% из подходящих.

Добавление нового значения в существующий атрибут делается конфигурацией. Добавление нового атрибута требует доработки бэкенда: сервис должен получать этот атрибут о клиенте. Откуда сервис берет атрибуты клиента, решает бэкенд (п. 13).

Попадание в долю показа определяется случайно при каждом событии. Если для анализа нужна контрольная группа (клиенты, которые подходили, но не получили опрос), такие случаи стоит логировать отдельно. Решение принимается вместе с аналитикой.

## 7. API (логическое описание)

Точные пути, формат и коды ответов определяет бэкенд. Ниже набор операций и требования к ним.

Общее для всех операций:
- доступны только авторизованному клиенту;
- клиент определяется сервисом по сессии или токену, фронт никогда не передает ID клиента в запросе;
- все операции с показом проверяют, что показ принадлежит текущему клиенту;
- если фронт передает ID объекта события (займа), сервис проверяет, что объект принадлежит клиенту, или сохраняет его только как справочный (решает бэкенд).

### 7.1. Получить активный опрос для шага флоу

Вход: код шага флоу, ID объекта события (необязательно).

Выход: либо «опроса нет», либо конфигурация опроса: ID и код опроса, заголовок, список шагов, в каждом шаге список вопросов с ID, типом, текстом, обязательностью и настройками.

Операция только читает данные и не создает показ. Показ создается отдельной операцией, когда поп-ап реально отрисован.

### 7.2. Зафиксировать показ

Вход: ID опроса, код шага флоу, ID объекта события (необязательно).

Выход: ID показа.

Сервис повторно проверяет правила показа. Если опрос уже показан сегодня (например, в другой вкладке), операция возвращает отказ, и фронт закрывает поп-ап.

### 7.3. Сохранить ответы шага

Вход: ID показа, номер шага, список ответов (ID вопроса и значение).

Проверки на сервисе:
- показ существует, принадлежит клиенту и не в статусе «закрыт» или «завершен»;
- все вопросы относятся к опросу показа и к переданному шагу;
- обязательные вопросы заполнены;
- значения соответствуют типу: число в границах шкалы, код варианта из списка, количество выбранных вариантов не больше максимума, длина текста не больше лимита;
- текст очищается от управляющих символов и обрезается по лимиту.

Повторная отправка того же шага перезаписывает ответы, а не создает дубли. Это защищает от двойного клика и повторов при сетевых ошибках.

Если сохраненный шаг последний, сервис сам переводит показ в статус «завершен». Фронту не нужно отдельно сообщать о завершении.

После каждого шага сервис обновляет у показа номер последнего шага.

### 7.4. Закрыть опрос

Вход: ID показа, номер шага, на котором закрыт.

Переводит показ в статус «закрыт» и сохраняет шаг закрытия. Ответы на предыдущие шаги сохраняются и считаются полученными. Если показ уже завершен, операция ничего не меняет.

## 8. Фронт

### 8.1. Типы вопросов

Каждый тип вопроса реализуется отдельным компонентом. Поп-ап собирает шаг из компонентов по конфигурации, полученной от сервиса.

| Тип | Вид | Настройки |
|---|---|---|
| Шкала | Ряд радио-кнопок с цифрами (как на текущем макете) | Минимум, максимум, подписи к краям шкалы |
| Текст | Многострочное поле | Плейсхолдер, максимальная длина |
| Выбор одного | Радио-кнопки списком | Список вариантов |
| Выбор нескольких | Чекбоксы | Список вариантов, максимум выбранных |
| Звезды | Ряд звезд | Количество звезд |

Шкала бывает двух видов: радиокнопки с цифрами (NPS 1–10; до 11 значений, должно помещаться на мобильной версии) и смайлики (CES 1–5: 😭 😒 😐 ☺️ 😍, после выбора остальные бледнеют).

Вопрос с условием showIf скрыт, пока ответ на вопрос-условие ему не подходит. Сервис не сохраняет ответы на скрытые вопросы, даже если фронт их прислал.

Итоговый список типов фиксируется по макетам из Figma. Если в макетах есть тип, которого нет в таблице, его нужно добавить до старта разработки.

Если сервис вернул вопрос с неизвестным фронту типом, фронт не показывает опрос целиком, а не ломает поп-ап.

### 8.2. Поведение поп-апа

- Заголовок опроса и индикатор шага («1/2») сверху, крестик в углу.
- Кнопка «Отправить» появляется, только когда заполнены обязательные вопросы шага (по макету ее нет до выбора оценки).
- После нажатия кнопка блокируется до ответа сервиса, чтобы исключить двойную отправку.
- После успешной отправки шага показывается следующий шаг, после последнего экран благодарности: «Спасибо, что помогаете становиться лучше!» и кнопка «Закрыть». Он закрывается кнопкой, крестиком или автоматически через несколько секунд.
- При ошибке сохранения шага: одна автоматическая повторная попытка, затем сообщение «Не удалось отправить, попробуйте еще раз» с возможностью повторить. Поп-ап не должен зависать.
- Крестик доступен на любом шаге, включая экран благодарности.
- Поп-ап закрывается также по клику вне окна и по клавише Esc. Такое закрытие фиксируется так же, как крестик.
- На мобильной версии сайта поп-ап открывается как нижняя шторка, клавиатура при вводе комментария не должна перекрывать кнопку «Отправить».

### 8.3. Встраивание в флоу

- На каждом шаге флоу из списка триггеров фронт вызывает одну общую функцию показа опроса с кодом шага и ID объекта события.
- Вызов делается после того, как основной контент шага загружен, и с задержкой 2 секунды, чтобы клиент сначала увидел результат шага (например, «Займ погашен»).
- Опрос не показывается поверх действий, обязательных для продолжения флоу (подписание документов, ввод кода из смс, оплата). Такие шаги не используются как триггеры.
- На запрос активного опроса стоит короткий таймаут (1–2 секунды). При таймауте или ошибке опрос не показывается, флоу продолжается без изменений.
- Защита от повторного вызова: если компонент шага перерисовывается, функция не запрашивает опрос повторно в рамках того же визита на шаг. Основная защита от повторов на сервере — правило «не чаще 1 раза в день».
- Если на экране уже открыто другое модальное окно, опрос не показывается.
- Если клиент обновил страницу в середине опроса, опрос не восстанавливается. Незавершенный показ остается в статусе «показан», ответы на пройденные шаги сохранены.

### 8.4. Веб-аналитика

Дополнительно к данным в БД можно отправлять события в систему веб-аналитики сайта (показ, ответ на шаг, закрытие). Это не замена данным в DWH. В первую версию не входит.

## 9. DWH и BI

- Схема или БД сервиса подключается к текущему механизму загрузки в DWH (репликация, CDC или ETL, как устроено для других сервисов).
- Загружаются все сущности как есть: опросы, вопросы, триггеры, показы, ответы. Без показов нельзя посчитать долю ответивших и шаг ухода.
- Сервис не считает метрики. Расчет NPS, CES и остальных показателей делается в BI.
- ID клиента хранится в том же формате, что в DWH. ID объекта события (займа) — в формате займов DWH.
- Частота загрузки: достаточно ежедневной.
- Для удобства BI полезна витрина: одна строка на «показ + вопрос» с кодом опроса, кодом вопроса, метрикой (CES/NPS), числовым и текстовым значением, результатом по вопросу (ответил / закрыл / не дошел), шагом флоу, ID займа, датой и атрибутами клиента. Кто делает витрину, решает DWH.

Что сможет считать BI:
- NPS и CES по опросу, шагу флоу, сегменту клиента, периоду;
- доля ответивших от показов отдельно по CES и NPS;
- доля закрывших опрос на каждом шаге;
- распределение оценок;
- связь оценки с последующим поведением клиента (повторный займ, просрочка, отток);
- динамика оценок одного клиента от займа к займу.

## 10. Тонкие места и решения по ним

### 10.1. Изменение опроса после запуска

Если изменить текст вопроса или варианты ответа у опроса, по которому уже есть ответы, старые ответы станут несопоставимы с новыми.

Правило: у активного опроса с ответами нельзя менять тексты вопросов, типы, варианты и шкалу. Для изменений создается новый опрос с новым кодом, старый переводится в архив. Допустимые изменения у активного опроса: статус, приоритет, даты, интервал показа, триггеры и условия.

### 10.2. Одновременные запросы

Клиент может открыть сайт в двух вкладках или фронт может вызвать показ дважды.

Решение: правило «не чаще 1 раза в день» повторно проверяется при фиксации показа (п. 7.2). Бэкенд решает, нужна ли блокировка на уровне клиента при создании показа.

### 10.3. Показ без отрисовки

Если фиксировать показ в момент запроса опроса, а поп-ап не отрисовался, в данных появятся ложные показы, и доля ответивших будет занижена.

Решение: запрос опроса только читает данные, показ фиксируется фронтом после фактической отрисовки поп-апа.

### 10.4. Незавершенные показы

Показы в статусе «показан» (клиент закрыл вкладку, обновил страницу) учитываются в правиле «не чаще 1 раза в день». Ответы на пройденные шаги считаются полученными, по остальным вопросам результат «не дошел».

### 10.5. Несколько событий за день

Если клиент за день дважды достиг одного события (например, два займа), опрос показывается только на первом. Это осознанное ограничение: вероятность редкая, а повторный опрос в тот же день раздражает.

Если два разных опроса привязаны к разным событиям одного дня (например, CES после заявки и CES+NPS после выдачи), каждый показывается, так как ограничение действует на каждый опрос отдельно. Если это окажется слишком частым, можно добавить общий дневной лимит на все опросы через конфиг сервиса.

### 10.6. Шаги флоу до авторизации

На шагах до авторизации ID клиента еще нет.

Решение на старте: опросы только для авторизованных клиентов. Список шагов флоу проверить на это ограничение.

### 10.7. Отображение комментариев

Текст комментария хранится как есть и при выводе в любых внутренних интерфейсах (отчеты, BI, будущая админка) должен экранироваться, чтобы исключить выполнение вредоносного кода, введенного в поле.

### 10.8. Защита от злоупотреблений

Без промокодов мотивации накручивать ответы почти нет, но базовая защита нужна:
- ограничение частоты запросов к сервису на одного клиента;
- лимит длины текста;
- правило «не чаще 1 раза в день» на опрос.

### 10.9. Аварийное отключение

Нужна возможность отключить все опросы без релиза (общий флаг в конфиге сервиса или на фронте). При выключенном флаге сервис всегда отвечает «опроса нет».

### 10.10. Часовой пояс

Все даты хранятся в UTC. Граница дня для правила «1 раз в день» считается по московскому времени. В DWH даты приводятся к принятому там часовому поясу.

### 10.11. Управление опросами без админки

На старте опросы заводятся разработчиком:
- конфигурацию каждого опроса готовит продукт в согласованном формате (таблица: вопросы, типы, варианты, шаги, триггеры, условия, доля показа);
- разработчик переносит ее в БД миграцией, это дает историю изменений;
- админка рассматривается во второй версии, если опросы и условия будут меняться чаще раза в месяц.

## 11. Мониторинг и логирование

- Метрики сервиса: число запросов активного опроса, доля ответов «опрос есть», число показов, ответов, закрытий, ошибок, время ответа.
- Алерт на рост ошибок и на время ответа выше таймаута фронта (иначе опросы перестанут показываться незаметно).
- В логах не писать тексты комментариев, только ID.

## 12. Триггеры (шаги флоу)

Решение продукта: на старте опрос только на оплате, остальные заведены выключенными.

| Код шага флоу | Шаг | Опрос | Шаги опроса | Состояние на старте |
|---|---|---|---|---|
| loan_repaid | Займ погашен | NPS + CES | 1 — NPS 1–10 (комментарий при 6 и ниже), 2 — CES про оплату (комментарий при 3 и ниже), как в макете | Включен, всем клиентам |
| loan_issued | Займ выдан | CES | CES, комментарий при оценке 3 и ниже | Выключен (DRAFT) |
| application_submitted | Заявка отправлена | CES | CES, комментарий при оценке 3 и ниже | Выключен (DRAFT) |

Выключенный опрос включается миграцией: `UPDATE survey SET status = 'ACTIVE' WHERE code = '…'`.

**На будущее: NPS на выдаче займа.** Опрос NPS + CES для `loan_issued` уже заведен в примерах как черновик (`nps_ces_loan_issued_draft`, статус DRAFT) и клиентам не показывается. Чтобы включить его, достаточно одной миграции без релиза кода:

```sql
UPDATE survey SET status = 'ARCHIVED' WHERE code = 'ces_loan_issued';
UPDATE survey SET status = 'ACTIVE' WHERE code = 'nps_ces_loan_issued_draft';
```

После этого на выдаче займа будет опрос из двух шагов, как на погашении: NPS, затем CES «Насколько легко было получить займ?». В проде вместо примера заводится свой опрос с утвержденными текстами.

Для каждого шага проверить: клиент авторизован, на экране нет обязательных действий, опрос уместен по смыслу шага (например, не показывать опрос сразу после отказа в займе, если это не опрос про отказ).

## 13. Вопросы до старта разработки

### 13.1. Решено

| Вопрос | Решение |
|---|---|
| Макеты | Figma «NPS CES», реализованы активные опросы. Пассивные («Оценить сервис») не в первой версии |
| Опросы на старте | Только на оплате: `loan_repaid`, NPS 1–10 → CES про оплату. CES на выдаче и после заявки заведены, но выключены; NPS на выдаче подготовлен черновиком (п. 12) |
| Шкалы | NPS 1–10 как в макете, CES 1–5 смайликами |
| Комментарий | Только при низкой оценке: NPS 6 и ниже, CES 3 и ниже |
| Граница дня для «1 раз в день» | Московское время |
| Задержка показа после события | 2 секунды |
| Экран благодарности | «Спасибо, что помогаете становиться лучше!», кнопка «Закрыть», автозакрытие через 4 секунды |
| Закрытие | Крестиком, клавишей Esc и кликом мимо окна, все засчитываются как закрытие |
| Общий лимит опросов в день | Не нужен: на старте один опрос. Если опросов станет больше, включается настройкой `SURVEY_GLOBAL_DAILY_LIMIT` |
| Доля показа | 100% подходящих клиентов |
| Контрольная группа | На старте не нужна |
| Данные для BI | Сырые таблицы в DWH (зеркало БД) и витрина «показ + вопрос» (`dwh/survey_question_result.sql`) |
| Персональные данные | Согласие дается при входе на сайт, данные в контуре компании, отдельная обработка не нужна |
| Платформа | Только сайт |
| Стек сервиса | Java 21, Spring Boot, PostgreSQL (как основной бэкенд); при необходимости можно переписать |

### 13.2. Осталось решить с техлидом и командами

В коде для каждого пункта уже есть рабочий вариант по умолчанию, вопрос в том, подходит ли он инфраструктуре.

| Вопрос | Кто | Как сделано сейчас |
|---|---|---|
| Отдельный сервис или модуль в текущем бэкенде | Техлид | Отдельный сервис, своя схема в существующем PostgreSQL ([integration.md](integration.md)) |
| Шаблон сервиса, CI/CD, мониторинг | Техлид | Dockerfile, health-проверки, метрики Prometheus, CI на GitHub Actions |
| Как сайт обращается к сервисам и как сервис узнает ID клиента | Техлид, бэкенд | Через API gateway: он авторизует клиента и передает ID в заголовке `X-Client-Id` |
| Откуда брать атрибуты клиента для условий показа | Бэкенд | HTTP-запрос к сервису клиентов. На старте условий нет, можно отложить |
| Проверять ли, что ID займа принадлежит клиенту | Бэкенд | Не проверяется, хранится как справочное значение |
| Лимит запросов | Бэкенд | В памяти сервиса, 60 запросов в минуту на клиента; при нескольких экземплярах лучше на gateway |
| Стек сайта и подключение виджета | Фронт | Виджет без зависимостей, подключается ES-модулем или тегом `<script>` |
| Общий механизм модальных окон | Фронт | Виджет не показывается, если на странице открыто окно с `aria-modal="true"`; можно передать свою проверку |
| Механизм загрузки в DWH и кто подключает схему | DWH | Зеркало БД, как у других сервисов |
| Формат ID клиента и займа | DWH | Строки до 100 символов, передаются как есть |

## 14. План работ

1. Ревью документа бэкендом, техлидом, фронтом, DWH, закрытие вопросов из п. 13.
2. Подготовка конфигурации первых опросов (CES, CES+NPS) по Figma.
3. Бэкенд: модель данных, миграции, первые опросы в БД.
4. Бэкенд: операции API, правила показа и гибкие условия, тесты на правила показа и валидацию ответов.
5. Фронт: компоненты типов вопросов и поп-ап.
6. Фронт: встраивание вызова на шаги флоу, аварийный флаг.
7. DWH: подключение загрузки сырых таблиц, витрина (если нужна).
8. BI: отчеты по NPS и CES.
9. Тестирование на стенде: правило «1 раз в день», повторное событие на следующий день, условия и доля показа, повторные отправки, закрытие на каждом шаге, ошибки сервиса, мобильная версия.
10. Запуск первого опроса, проверка данных в DWH и BI через несколько дней после запуска.
